# Database Schema (MVP)

PostgreSQL 16 schema for the Casino Platform MVP. The executable version of this document is
[`backend/migrations/001_initial_schema.sql`](../backend/migrations/001_initial_schema.sql);
this file explains the *why* behind each table.

## Design conventions

| Convention | Rule |
| --- | --- |
| Primary keys | `UUID` generated by `uuid_generate_v4()` from the `"uuid-ossp"` extension. |
| Money | `NUMERIC(18,2)`. Never `FLOAT`/`REAL` — binary floating point cannot represent cents exactly. |
| Timestamps | `TIMESTAMPTZ`, default `now()`, always stored in UTC. |
| Balances | **Never stored.** Derived from `transactions` with `SUM(amount)`. |
| Ledger | `transactions` is append-only. Corrections are new compensating rows, never `UPDATE`s. |
| Sign convention | Credits are **positive** (`deposit`, `win`), debits are **negative** (`bet`, `withdraw`). |
| Naming | `snake_case`, plural table names, `<table>_<rule>_check` constraint names. |

## Entity relationships

```
users (1) ──< (N) transactions      # every money movement belongs to one user
users (1) ──< (N) game_rounds       # every wheel spin belongs to one user

game_rounds.id ─ ─ ─ transactions.reference_id   # soft link (VARCHAR), not a foreign key
```

`transactions.reference_id` deliberately stays a `VARCHAR` instead of a hard foreign key: the same
column also correlates deposits/withdrawals with external payment providers, not only game rounds.

## 1. `users`

Platform accounts — both players and operators live in this table.

```sql
CREATE TABLE users (
    id            UUID         PRIMARY KEY DEFAULT uuid_generate_v4(),
    phone         VARCHAR(20)  NOT NULL,
    password_hash VARCHAR(255) NOT NULL,
    role          VARCHAR(20)  NOT NULL DEFAULT 'user',
    created_at    TIMESTAMPTZ  NOT NULL DEFAULT now(),
    updated_at    TIMESTAMPTZ  NOT NULL DEFAULT now(),

    CONSTRAINT users_phone_key  UNIQUE (phone),
    CONSTRAINT users_role_check CHECK (role IN ('user', 'admin'))
);

CREATE INDEX idx_users_phone ON users (phone);
```

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `UUID` | Primary key, generated by the database. |
| `phone` | `VARCHAR(20)` | Unique login identifier. Uniqueness is enforced by `users_phone_key`. |
| `password_hash` | `VARCHAR(255)` | bcrypt hash only — plaintext passwords must never reach the database. |
| `role` | `VARCHAR(20)` | `'user'` or `'admin'` (CHECK constraint), default `'user'`. |
| `created_at` | `TIMESTAMPTZ` | Row creation time (UTC). |
| `updated_at` | `TIMESTAMPTZ` | Maintained by the `trg_users_set_updated_at` trigger — the application never sets it by hand. |

## 2. `transactions`

The wallet ledger: **the single source of truth for money**. One row per money movement.

```sql
CREATE TABLE transactions (
    id           UUID          PRIMARY KEY DEFAULT uuid_generate_v4(),
    user_id      UUID          NOT NULL,
    type         VARCHAR(20)   NOT NULL,
    amount       NUMERIC(18,2) NOT NULL,
    status       VARCHAR(20)   NOT NULL DEFAULT 'completed',
    reference_id VARCHAR(64),
    created_at   TIMESTAMPTZ   NOT NULL DEFAULT now(),

    CONSTRAINT transactions_user_id_fkey
        FOREIGN KEY (user_id) REFERENCES users (id) ON DELETE CASCADE,
    CONSTRAINT transactions_type_check
        CHECK (type IN ('deposit', 'withdraw', 'bet', 'win')),
    CONSTRAINT transactions_status_check
        CHECK (status IN ('pending', 'completed', 'failed', 'cancelled')),
    CONSTRAINT transactions_amount_nonzero_check
        CHECK (amount <> 0),
    CONSTRAINT transactions_amount_sign_check
        CHECK (
            (type IN ('deposit', 'win')  AND amount > 0) OR
            (type IN ('withdraw', 'bet') AND amount < 0)
        )
);

CREATE INDEX idx_transactions_user_created  ON transactions (user_id, created_at DESC);
CREATE INDEX idx_transactions_type          ON transactions (type);
CREATE INDEX idx_transactions_status        ON transactions (status);
CREATE INDEX idx_transactions_reference_id  ON transactions (reference_id) WHERE reference_id IS NOT NULL;
```

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `UUID` | Primary key. |
| `user_id` | `UUID` | FK → `users.id`, `ON DELETE CASCADE`. Every movement belongs to exactly one user. |
| `type` | `VARCHAR(20)` | `'deposit'`, `'withdraw'`, `'bet'`, `'win'`. |
| `amount` | `NUMERIC(18,2)` | **Signed**: positive credits the wallet, negative debits it. |
| `status` | `VARCHAR(20)` | `'pending'`, `'completed'`, `'failed'`, `'cancelled'`. Defaults to `'completed'`. |
| `reference_id` | `VARCHAR(64)` | Optional correlation key: a `game_rounds.id` or an external payment id. |
| `created_at` | `TIMESTAMPTZ` | When the movement happened. Rows are never back-dated. |

### How the balance works

```sql
-- Current balance of one user (only completed rows count)
SELECT COALESCE(SUM(amount), 0) AS balance
FROM transactions
WHERE user_id = $1
  AND status  = 'completed';
```

The same calculation is exposed as the `account_balances` view (section 4). A typical settled
wheel spin therefore writes **two** rows, both referencing the same round:

| type | amount | reference_id |
| --- | --- | --- |
| `bet` | `-10.00` | `game_rounds.id` |
| `win` | `+35.00` | `game_rounds.id` (only on a win) |

### Why an append-only ledger instead of `users.balance`?

- **Auditability** — every cent has a row explaining where it came from; nothing is overwritten.
- **No lost updates** — `UPDATE users SET balance = balance - 10` under concurrent bets is a race
  condition and can oversell a balance. Inserting rows is safe.
- **Disputes** — support can replay a user's history and prove the balance.
- **Reconciliation** — payment-provider settlements can be matched via `reference_id`.

### Integrity rules enforced by the schema

- `transactions_amount_sign_check` — a `bet`/`withdraw` **must** be negative and a `deposit`/`win`
  **must** be positive, so a client bug cannot credit money with the wrong type.
- `transactions_amount_nonzero_check` — zero-value noise rows are rejected.
- `status` — only `'completed'` rows count toward a balance, so a pending deposit cannot be staked.

## 3. `game_rounds` (wheel + slots)

One row per round. The round stores *what was staked*, *what came out*, and the provably-fair
commitment for that spin.

```sql
CREATE TABLE game_rounds (
    id               UUID          PRIMARY KEY DEFAULT uuid_generate_v4(),
    user_id          UUID          NOT NULL,
    bet_amount       NUMERIC(18,2) NOT NULL,
    bet_type         VARCHAR(20)   NOT NULL,
    bet_value        VARCHAR(64),          -- widened by 011_keno.sql (keno picks)
    result           VARCHAR(64),           -- widened by 005_slots_3x3.sql
    payout           NUMERIC(18,2) NOT NULL DEFAULT 0,
    multiplier       NUMERIC(6,2),           -- added by 003_spin_wheel.sql
    crash_point      NUMERIC(10,2),          -- added by 007_aviator.sql
    started_at       TIMESTAMPTZ,            -- added by 007_aviator.sql
    settled_at       TIMESTAMPTZ,            -- added by 007_aviator.sql
    status           VARCHAR(12)   NOT NULL DEFAULT 'settled',  -- 007_aviator.sql
    server_seed_hash VARCHAR(64)   NOT NULL,
    created_at       TIMESTAMPTZ   NOT NULL DEFAULT now(),

    CONSTRAINT game_rounds_user_id_fkey
        FOREIGN KEY (user_id) REFERENCES users (id) ON DELETE CASCADE,
    CONSTRAINT game_rounds_bet_amount_check
        CHECK (bet_amount > 0),
    CONSTRAINT game_rounds_bet_type_check
        CHECK (bet_type IN ('red', 'black', 'green', 'even', 'odd', 'low', 'high', 'number', 'spin', 'slots', 'dice', 'aviator', 'plinko', 'keno', 'baccarat', 'dragontiger', 'teenpatti', 'cascade', 'classic_roulette', 'fruit_bonanza', 'dice3d', 'boxing_king')),
    CONSTRAINT game_rounds_status_check
        CHECK (status IN ('pending', 'cashed_out', 'crashed', 'settled')),
    CONSTRAINT game_rounds_payout_check
        CHECK (payout >= 0),
    CONSTRAINT game_rounds_server_seed_hash_check
        CHECK (server_seed_hash ~ '^[0-9a-f]{64}$')
);

CREATE INDEX idx_game_rounds_user_created ON game_rounds (user_id, created_at DESC);
```

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `UUID` | Primary key. Also used as `transactions.reference_id` for the round's bet/win rows. |
| `user_id` | `UUID` | FK → `users.id`, `ON DELETE CASCADE`. |
| `bet_amount` | `NUMERIC(18,2)` | Stake placed, always > 0 (the debit is the matching `bet` transaction). |
| `bet_type` | `VARCHAR(20)` | `'spin'` (wheel), `'slots'`, `'dice'`, `'aviator'`, `'plinko'`, `'keno'`, `'baccarat'`, `'dragontiger'`, `'teenpatti'`, `'cascade'`, `'classic_roulette'`, `'fruit_bonanza'`, `'dice3d'` or `'boxing_king'`. The original values (`'red'`…`'number'`) are retained for historical rows from the first roulette table. Added by `020_boxing_king.sql`. |
| `bet_value` | `VARCHAR(64)` | The call for `'dice'` (`'high'`/`'low'`), the player's picks for `'keno'` (`'3,17,42'`), the side for `'baccarat'` / `'dragontiger'` (`'player'`/`'banker'`/`'tie'`, `'dragon'`/`'tiger'`/`'tie'`), the row count for `'plinko'`, the backed bet for `'classic_roulette'` (`'number:17'`, `'red'`, `'odd'`, …), the call for `'dice3d'` (`'high'`, `'low'`, `'15'`); `NULL` for `'teenpatti'`, `'cascade'`, `'fruit_bonanza'`, `'boxing_king'` and where the player picks no target. Widened from 10 by `011_keno.sql`. |
| `result` | `VARCHAR(64)` | What landed: the wheel multiplier as text (`'0'`, `'0.5'`, `'10'`), the row-major slot grid (9 cells), the dice roll (`'73'`), the Aviator crash point (`'3.47'`) once settled, the 20 drawn keno numbers (`'4,8,9,…'`), the baccarat winner plus both hands (`'banker\|P:AS,5H\|B:KH,2C,7S'`), the dragon tiger winner plus both cards (`'dragon\|D:KS\|T:9H'`), the teen patti winner, both categories and both hands (`'player\|pair/high\|P:AS,AH,KD\|D:7C,9H,KS'`), the cascade summary (`'3c\|4x\|2.41x'`), the roulette pocket plus its colour (`'17\|black'`, `'0\|green'`), the nine fruit symbols row-major (`'🍉🍇🍋🍒🍊⭐🍉🍇🍋'`), the three dice plus their total (`'4,2,3\|9'`), or the nine boxing symbols row-major (`'🥊🥊🥊🏆🤴💪💥🩳🏆'`). |
| `crash_point` | `NUMERIC(10,2)` | **Aviator only**: the hidden burst multiplier. Written at `start`, revealed to the client only after the round settles. |
| `started_at` | `TIMESTAMPTZ` | **Aviator only**: server clock at round open. Cash-out validity is `now() − started_at`, so the client cannot influence it. |
| `settled_at` | `TIMESTAMPTZ` | **Aviator only**: when the round was cashed out or burst. |
| `status` | `VARCHAR(12)` | `'pending'` (flying) → `'cashed_out'` / `'crashed'`; `'settled'` for the instant games (the default). |

## 3b. `mines_games` (migration `008_mines.sql`)

One row per Mines board. Mines is turn-based, so it keeps its own state instead of the
instant-round `game_rounds` table.

```sql
CREATE TABLE mines_games (
    id               UUID          PRIMARY KEY DEFAULT uuid_generate_v4(),
    user_id          UUID          NOT NULL REFERENCES users (id) ON DELETE CASCADE,
    bet_amount       NUMERIC(18,2) NOT NULL CHECK (bet_amount > 0),
    mines_count      SMALLINT      NOT NULL CHECK (mines_count BETWEEN 1 AND 24),
    grid_state       JSONB         NOT NULL,                       -- 25 booleans, true = mine
    revealed_tiles   JSONB         NOT NULL DEFAULT '[]'::jsonb,   -- indices of opened gems
    status           VARCHAR(10)   NOT NULL DEFAULT 'active',      -- active | won | lost
    multiplier       NUMERIC(14,2) NOT NULL DEFAULT 1,
    payout           NUMERIC(18,2) NOT NULL DEFAULT 0,
    server_seed_hash VARCHAR(64)   NOT NULL,
    created_at       TIMESTAMPTZ   NOT NULL DEFAULT now(),
    settled_at       TIMESTAMPTZ
);
```

| Column | Notes |
| --- | --- |
| `grid_state` | The hidden layout. **Never serialised to a client** until the game settles. |
| `revealed_tiles` | Indices the player opened (used to recompute the multiplier server-side). |
| `status` | `active` → `won` (cash-out or board cleared) / `lost` (hit a mine). |
| `multiplier` / `payout` | Locked in at settle: `payout = bet_amount × multiplier`. |
| `revealed_tiles` + `multiplier` | `GET /game/mines/current` returns these so a reloaded page can resume. |

The ledger still records every movement: `bet` (negative) at `start` and `win` (positive) at
`cashout`, both referencing `mines_games.id` as `reference_id`.

## 3c. `blackjack_games` (migration `010_blackjack.sql`)

One row per hand. Also turn-based, so it owns its state (and its shuffled shoe).

```sql
CREATE TABLE blackjack_games (
    id               UUID          PRIMARY KEY DEFAULT uuid_generate_v4(),
    user_id          UUID          NOT NULL REFERENCES users (id) ON DELETE CASCADE,
    bet_amount       NUMERIC(18,2) NOT NULL CHECK (bet_amount > 0),
    player_hand      JSONB         NOT NULL DEFAULT '[]'::jsonb,  -- e.g. ["AS","TH"]
    dealer_hand      JSONB         NOT NULL DEFAULT '[]'::jsonb,  -- 2 cards; [1] is the hole card
    deck             JSONB         NOT NULL,                      -- remaining cards of the shoe
    status           VARCHAR(10)   NOT NULL DEFAULT 'active',      -- active | won | lost | push
    payout           NUMERIC(18,2) NOT NULL DEFAULT 0,
    server_seed_hash VARCHAR(64)   NOT NULL,
    created_at       TIMESTAMPTZ   NOT NULL DEFAULT now(),
    settled_at       TIMESTAMPTZ
);
```

| Column | Notes |
| --- | --- |
| `dealer_hand` | Stored complete, but the API returns **only index 0** while `status = 'active'`. |
| `deck` | The committed, shuffled shoe. Never serialised to a client. |
| `payout` | `2 × bet` on a win, `bet` on a push, `0` on a loss. |
| Resume | `GET /game/blackjack/current` returns your hand + the up-card; HIT/STAND continue the row. |
| `multiplier` | `NUMERIC(6,2)` | The payout multiplier used (`0`, `2`, `10`, …); `payout = bet_amount × multiplier`. `NULL` on legacy roulette rows. |
| `payout` | `NUMERIC(18,2)` | Amount credited back to the player (stake included). `0` on a 0× spin. |
| `server_seed_hash` | `VARCHAR(64)` | Hex SHA-256 commitment of the server seed, published before the spin. |
| `created_at` | `TIMESTAMPTZ` | Round time. |

**Why `result` is nullable:** the schema still allows a round to be opened before it settles (the
hash is known at accept time), which keeps the crash-safe audit trail from the original design. The
current wheel settles in a single transaction, so a row is written complete and `result` is
practically never `NULL`.

```sql
SELECT id FROM game_rounds WHERE result IS NULL AND created_at < now() - interval '5 minutes';
```

**Relationship to money:** the stake and the win are *not* duplicated as columns-only truth — they
are recorded in `transactions` (`bet` then optional `win`), and `payout` mirrors the credited amount
for fast reporting. `game_rounds` answers "how did this round play out?", `transactions` answers
"what happened to the wallet?".

## 4. `payment_requests` (migration `002_payment_requests.sql`)

Manual deposit / withdrawal requests that an operator approves or rejects — the bridge until a real
payment gateway is integrated.

```sql
CREATE TABLE payment_requests (
    id          UUID          PRIMARY KEY DEFAULT uuid_generate_v4(),
    user_id     UUID          NOT NULL,
    amount      NUMERIC(18,2) NOT NULL,
    type        VARCHAR(20)   NOT NULL,
    status      VARCHAR(20)   NOT NULL DEFAULT 'pending',
    reviewed_by UUID,
    reviewed_at TIMESTAMPTZ,
    created_at  TIMESTAMPTZ   NOT NULL DEFAULT now(),
    updated_at  TIMESTAMPTZ   NOT NULL DEFAULT now(),

    CONSTRAINT payment_requests_user_id_fkey
        FOREIGN KEY (user_id) REFERENCES users (id) ON DELETE CASCADE,
    CONSTRAINT payment_requests_reviewed_by_fkey
        FOREIGN KEY (reviewed_by) REFERENCES users (id) ON DELETE SET NULL,
    CONSTRAINT payment_requests_amount_check CHECK (amount > 0),
    CONSTRAINT payment_requests_type_check   CHECK (type IN ('deposit', 'withdraw')),
    CONSTRAINT payment_requests_status_check CHECK (status IN ('pending', 'approved', 'rejected'))
);
```

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `UUID` | Also used as `transactions.reference_id` for the money rows belonging to it. |
| `user_id` | `UUID` | FK → `users.id`. |
| `amount` | `NUMERIC(18,2)` | Always positive; direction comes from `type`. |
| `type` | `VARCHAR(20)` | `'deposit'` or `'withdraw'`. |
| `status` | `VARCHAR(20)` | `'pending'` (default) → `'approved'` or `'rejected'`. |
| `reviewed_by` | `UUID` | Admin who reviewed it (audit trail), NULL while pending. |
| `reviewed_at` | `TIMESTAMPTZ` | When it was reviewed. |
| `created_at` / `updated_at` | `TIMESTAMPTZ` | `updated_at` is maintained by the `set_updated_at` trigger. |

### Money flow

| Request | On approval | On rejection |
| --- | --- | --- |
| `deposit` | a `deposit` ledger row credits the wallet | nothing was written, nothing to undo |
| `withdraw` | nothing — the debit already happened when filed | a compensating `deposit` row refunds the wallet |

A withdrawal is debited **immediately** as a *completed* `withdraw` row. The ledger only counts
`completed` rows toward a balance, so a `pending` *transaction* would leave the funds spendable twice;
the waiting state lives on `payment_requests.status` instead.

## 5. `account_balances` (derived view)

A read-only convenience view so no code has to re-implement the ledger sum.

```sql
CREATE OR REPLACE VIEW account_balances AS
SELECT
    u.id                                      AS user_id,
    COALESCE(SUM(t.amount), 0)::NUMERIC(18,2) AS balance,
    COUNT(t.id)                               AS transaction_count,
    MAX(t.created_at)                         AS last_transaction_at
FROM users u
LEFT JOIN transactions t
       ON t.user_id = u.id
      AND t.status = 'completed'
GROUP BY u.id;
```

- A brand-new user with no transactions still appears, with `balance = 0` (`LEFT JOIN` + `COALESCE`).
- Only `status = 'completed'` rows are summed; `pending`/`failed`/`cancelled` are ignored.
- It is a view, not a table: it can never drift out of sync with the ledger.

## 6. Index summary

| Index | Table | Purpose |
| --- | --- | --- |
| `users_phone_key` (unique) | `users` | Login lookup and phone uniqueness. |
| `idx_users_phone` | `users` | Redundant-but-cheap lookup path kept for symmetric planner behaviour. |
| `idx_transactions_user_created` | `transactions` | Balance (`SUM`) and paginated history per user. |
| `idx_transactions_type` / `idx_transactions_status` | `transactions` | Admin reporting and reconciliation filters. |
| `idx_transactions_reference_id` (partial) | `transactions` | Join ledger rows to a `game_rounds` round or payment id. |
| `idx_game_rounds_user_created` | `game_rounds` | A player's round history, newest first. |

## 7. Deliberately out of scope for the MVP

These are **not** in the migrations yet and will arrive as later ones:

- `server_seed`, `client_seed`, `nonce` and `revealed_at` on `game_rounds` (needed to *verify* a spin).
- Provider tables for a real payment gateway (bKash etc.) — `payment_requests` is the manual bridge.
- `refund` and `bonus` transaction types (would need the sign CHECK constraint extended).
- Row-level security and a `sessions`/`refresh_tokens` table.
